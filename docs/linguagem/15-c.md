# Referência da Linguagem — 15. O C na Jinga

A biblioteca padrão do C (C11) faz parte da Jinga: as funções, os tipos e as
constantes dos cabeçalhos do C se chamam direto, com ponteiro de verdade e a
sintaxe do C. O cabeçalho se importa como no C, e o resto vem dele.

```ps
import <stdio.h>

printf("olá, %s! %d + %d = %d\n", "mundo", 2, 3, 2 + 3)
puts("o puts põe a quebra de linha sozinho")
```

```saida
olá, mundo! 2 + 3 = 5
o puts põe a quebra de linha sozinho
```

Este capítulo é a parte da linguagem: o import, os tipos, o ponteiro, o
cast, a chamada e o que derruba o programa. A referência de cada função, tipo
e constante, traduzida da cppreference, está em [docs/c/](../c/c.md), uma
página por cabeçalho.

O desenho parte do que já existe há décadas: a lista de cabeçalhos e funções
é a do padrão C11 (ISO/IEC 9899:2011, Anexo B do N1570); a chamada e os
callbacks passam pela libffi, a mesma que o `ctypes` do Python usa; as regras
de conversão entre a Jinga e o C são as da FFI do LuaJIT
([FFI Semantics](https://luajit.org/ext_ffi_semantics.html)), adaptadas.

Verificado na VM.

## 15.1. `import <stdio.h>` — o cabeçalho, igual ao `#include`

Um `import <cabeçalho.h>` por cabeçalho, no topo do arquivo, como o
`#include` do C. Os nomes do cabeçalho ficam soltos, como no C: `printf`, e
não `stdio.printf`. Importar o mesmo cabeçalho duas vezes vale uma.

Sem o import, o nome do C não existe, e o erro diz qual import falta, antes
de rodar:

```ps
printf("oi\n")     # NameError: sem o import <stdio.h>, o printf não existe
```

```saida
```

```erro
NameError: name 'printf' is not defined. Did you forget to import <stdio.h>?
```

O mesmo vale pro tipo do C escrito no programa (`FILE *f`, `size_t n`,
`struct tm *t`) e pro `offsetof`, que é do `<stddef.h>`.

- **O nome que o C declara em mais de um cabeçalho vale por qualquer um
  deles**, como no C: o `NULL` e o `size_t` vêm com o `<stddef.h>`, o
  `<stdio.h>`, o `<stdlib.h>`, o `<string.h>` ou o `<time.h>`.
- **O cabeçalho que inclui outro traz os nomes dele**: o `<inttypes.h>` traz
  o `<stdint.h>` (C11 7.8).
- **As palavras do C não pedem import**, como no C: `int *p`, `unsigned`,
  `const`, `volatile`, `struct`, `union`, `typedef`, `sizeof` e o cast.
- O import vale pro arquivo inteiro; dentro de uma funct ou de um bloco ele
  é `SyntaxError`.

```ps
import <string.h>
import <inttypes.h>

size_t n = strlen("Jinga")
int *p = NULL
int32_t maior = INT32_MAX
post(n, p == NULL, maior)
```

```saida
5 True 2147483647
```

Os cabeçalhos que a Jinga tem, cada um com a sua página:

| Cabeçalho | O que traz |
|---|---|
| [`<ctype.h>`](../c/ctype.md) | classificação e caixa de caracteres |
| [`<errno.h>`](../c/errno.md) | o `errno` e os códigos `EDOM`, `ERANGE`, `EILSEQ` |
| [`<float.h>`](../c/float.md) | os limites do ponto flutuante |
| [`<inttypes.h>`](../c/inttypes.md) | os formatos `PRId64`..., `imaxabs`, `strtoimax` (e o `<stdint.h>`) |
| [`<limits.h>`](../c/limits.md) | os limites dos inteiros (`INT_MAX`, `CHAR_BIT`...) |
| [`<math.h>`](../c/math.md) | a matemática (`sqrt`, `sin`, `floor`...) |
| [`<stdbool.h>`](../c/stdbool.md) | o `bool` |
| [`<stddef.h>`](../c/stddef.md) | `size_t`, `ptrdiff_t`, `NULL`, `offsetof` |
| [`<stdint.h>`](../c/stdint.md) | os inteiros de largura fixa (`int32_t`, `uint8_t`...) |
| [`<stdio.h>`](../c/stdio.md) | entrada e saída (`printf`, `scanf`, `fopen`...) |
| [`<stdlib.h>`](../c/stdlib.md) | memória, conversão, `qsort`, `exit`... |
| [`<string.h>`](../c/string.md) | texto e memória do C (`strlen`, `strcpy`, `memcpy`...) |
| [`<time.h>`](../c/time.md) | data e hora (`time`, `gmtime`, `strftime`...) |

O import de um cabeçalho do C11 que a Jinga não tem é `ImportError`, com o
motivo:

| Cabeçalho | Por quê |
|---|---|
| `<setjmp.h>` | pular por cima da VM corrompe a VM; a Jinga tem `try`/`catch` |
| `<stdarg.h>` | o `va_list` só existe dentro de uma função variádica do C |
| `<threads.h>`, `<stdatomic.h>` | a VM roda numa thread só, e funct da Jinga em outra thread corrompe a VM |
| `<assert.h>` | o `assert` da Jinga faz esse papel (levanta `AssertionError` com a linha) |
| `<iso646.h>` | são outros nomes pros operadores (`bitand`, `xor`...), gramática e não biblioteca |
| `<stdalign.h>`, `<stdnoreturn.h>` | são palavras da gramática do C, não biblioteca |
| `<signal.h>`, `<locale.h>`, `<wchar.h>`, `<wctype.h>`, `<uchar.h>`, `<fenv.h>`, `<complex.h>`, `<tgmath.h>` | ainda não estão na Jinga (são a segunda parte da biblioteca do C) |

## 15.2. Nome que existe nos dois: vale o da Jinga

Nenhum programa muda de sentido por importar um cabeçalho:

- `round`, `abs` e `pow` são os da Jinga, mesmo com o `<math.h>` ou o
  `<stdlib.h>` importado. O do C continua à mão pelo outro nome que o próprio
  C tem: `lround`/`llround`, `labs`/`llabs`/`fabs`, `powf`/`powl`.
- Numa variável da Jinga, `int`, `char`, `long` e `bool` são os da Jinga:
  `int x = 5` tem 64 bits, e `char c = 'a'` é o texto `"a"`. Na memória do C
  (o que o ponteiro aponta, o elemento de array, o campo de struct, o cast, o
  `sizeof`, o protótipo das funções do C), `int` é o `int` do C (4 bytes),
  `char` é o `char` do C (um byte, número), `long` é o `long` do C e `bool` é
  o `_Bool`.
- O nome que o programa liga esconde o do C, como esconde um builtin: `int
  time = 5` ou `funct free()`.

O `round` da Jinga arredonda o meio pro par (`2.5` dá `2`, como no Python); o
do C arredonda pra longe do zero, pelo `lround`:

```ps
import <stdio.h>
import <math.h>

printf("%.4f %d %ld\n", sqrt(2.0), round(2.5), lround(2.5))
```

```saida
1.4142 2 3
```

## 15.3. Os tipos do C

A variável declarada com um tipo do C guarda o valor no tipo do C, e **toda
escrita converte** pra ele, dando a volta como a atribuição do C:

```ps
import <stddef.h>

size_t n = 5
n = n - 6
unsigned char b = 255
b++
float f = 0.1
const int k = 7
post(n, b, f, k)
```

```saida
18446744073709551615 0 0.10000000149011612 7
```

**A conta é sempre a da Jinga**, com o valor já lido da memória do C (`v[i] /
2` dá `flo`, como `7 / 2`). O C manda na hora de **guardar**: escrever na
memória do C converte pro tipo de lá. É a regra da FFI do LuaJIT: o número
continua da linguagem, e o tipo do C vale na memória do C.

```ps
import <stdlib.h>

int x = 2147483647
x = x + 1
int *p = malloc(sizeof(int))
*p = x
char c = 'a'
post(x, *p, c, sizeof(int))
free(p)
```

```saida
2147483648 -2147483648 a 4
```

Na fronteira entre a Jinga e o C:

| Tipo do C | A Jinga lê como | A Jinga escreve a partir de |
|---|---|---|
| inteiros (`char` a `long long`, com e sem `unsigned`, `size_t`, `int32_t`...) | `int` (acima de 2^63, inteiro grande) | `int` e `bool`; fora da faixa dá a volta |
| `float`, `double`, `long double` | `flo` (o `long double` perde o que passa do `double`) | `flo` e `int` |
| `_Bool` | `bool` | `bool` e `int` |
| `T *` | ponteiro | ponteiro compatível, `NULL` (o `Null`), array de `T` (o endereço do primeiro) |
| `const char *` | ponteiro (`str(p)` traz o texto) | também `str`, copiado pra chamada e válido só durante ela |
| `T[N]`, `struct`, `union` | o próprio objeto do C | — |

O que não cabe é erro, antes de rodar quando o tipo se sabe: o inteiro não
vira ponteiro sem cast (`int não vira int * sem cast`), o `flo` não vira
inteiro calado (`flo não vira size_t calado: converta com int(x)`), e o `str`
da Jinga só entra onde o C não escreve (`const char *`).

## 15.4. Ponteiro

Tudo como no C: `*p`, `p[i]`, `p + n`, `p - q`, `p == q`, `p < q`, `if p`
(falso quando é `NULL`), o cast e o `sizeof`.

```ps
import <stdio.h>
import <stdlib.h>

int n = 5
int *v = malloc(n * sizeof(int))
int i = 0
while (i < n) {
    v[i] = i * i
    i++
}
int *p = v + 2
printf("%d %d %d\n", *p, p[1], *(v + 4))
printf("%td %zu\n", p - v, sizeof(int))
free(v)
```

```saida
4 9 16
2 4
```

- `malloc`/`free` são os do C: a memória não passa pelo coletor da Jinga.
- `NULL` é o `Null` da Jinga, e o ponteiro nulo que uma função devolve chega
  como `Null`.
- `post(p)` mostra `(int *) 0x...`, e `type(p)` dá `int *`.

**`&x`.** A variável cujo endereço é tomado passa a morar na memória do C,
com o tipo do C do nome dela (aqui, o `int` de 4 bytes), porque é isso que a
função do C vai escrever:

```ps
import <stdio.h>

int idade = 0
printf("idade: ")
if scanf("%d", &idade) == 1 {
    printf("ano que vem: %d\n", idade + 1)
}
```

```entrada
41
```

```saida
idade: ano que vem: 42
```

## 15.5. Array, struct, union e typedef

`char buf[64]`, `int v[6] = {5, 3, 9}` e `struct tm t`: a memória é da
variável, nasce zerada sem o `=` e vale enquanto ela existir (ponteiro pra
ela depois disso fica pendurado, como no C). `b = a` copia pra dentro da
memória de `b`; `&v` é o endereço dela. Na comparação, o array vira o
endereço do primeiro elemento, como no C.

```ps
import <stdio.h>
import <string.h>

str nome = "Jinga"
char buf[32]
strcpy(buf, nome)
strcat(buf, " + C")
printf("%s tem %zu bytes\n", buf, strlen(buf))
str volta = str(buf)
post(volta.upper())
```

```saida
Jinga + C tem 9 bytes
JINGA + C
```

O `struct`, o `union` e o `typedef` se declaram no topo do arquivo, com a
sintaxe do C e um campo por linha; o struct pode apontar pra si mesmo.
`p->campo` lê pelo ponteiro, `s.campo` pela variável:

```ps
import <stdio.h>
import <stdlib.h>

struct ponto {
    int x
    int y
}

struct ponto *ps = calloc(3, sizeof(struct ponto))
ps[1].x = 10
struct ponto *q = ps + 2
q->y = 20
printf("%d %d %d %zu\n", ps[0].x, ps[1].x, ps[2].y, sizeof(struct ponto))
free(ps)
```

```saida
0 10 20 8
```

Os structs do padrão vêm com o cabeçalho deles:

```ps
import <stdio.h>
import <time.h>

time_t zero = 0
struct tm *t = gmtime(&zero)
printf("%d-%02d-%02d, dia %d da semana\n", t->tm_year + 1900, t->tm_mon + 1, t->tm_mday, t->tm_wday)
char buf[64]
strftime(buf, sizeof(buf), "%A, %d de %B de %Y", t)
post(str(buf))
```

```saida
1970-01-01, dia 4 da semana
Thursday, 01 de January de 1970
```

```ps
import <stddef.h>

typedef struct {
    double x
    double y
} Ponto

Ponto a = {1.5, 2.5}
Ponto b
b = a
b.x = 9.0
post(a.x, b.x, sizeof(Ponto), offsetof(Ponto, y))
```

```saida
1.5 9.0 16 8
```

## 15.6. O cast do C

`(T) x` é o cast do C: o inteiro e o ponteiro viram um o outro (o
endereço), o `flo` vira inteiro cortado na direção do zero, todo ponteiro
vira qualquer ponteiro, e o resto é a conversão da escrita (o inteiro dá a
volta no tamanho do tipo). No cast, `int`, `char`, `long` e `bool` são os do
C; `flo`, `str` e os tipos só da Jinga continuam a chamada de sempre
(`(flo)(2)` é `flo(2)`).

```ps
import <stdlib.h>

int x = 5
post((int) x, (int)(3.7), (char)(65), (unsigned char) 300, (int) -2.9)
void *v = malloc(8)
int *ip = (int *) v
*ip = 7
post(*(int *) v, type((char *) ip))
free(v)
```

```saida
5 3 65 44 -2
7 char *
```

## 15.7. A chamada

- Cada função tem o protótipo do padrão, e a quantidade e o tipo de cada
  argumento são conferidos antes de rodar, com as frases que a chamada daria
  rodando (`strlen() takes exactly one argument (2 given)`, `sqrt(): o
  argumento 1 é double no C, e veio str`). A função do C não recebe argumento
  com nome.
- As variádicas (`printf`, `scanf`, `fprintf`, `sscanf`...) são guiadas pelo
  formato: cada argumento vai no tipo que a conversão pede (`%d` int, `%ld`
  long, `%zu` size_t, `%f` double, `%s` char *). Com o formato escrito no
  código, a conferência é antes de rodar (`printf: %d espera int, recebeu
  str`); com o formato numa variável, é na chamada, com a mesma frase.
- O `errno` é guardado logo depois de cada chamada, porque a própria VM pode
  mexer nele antes da linha seguinte (é o que o `ctypes` do Python faz).
  `errno = 0` escreve nele, e vale na chamada seguinte.

O C não levanta exceção: devolve um código e põe o motivo no `errno`:

```ps
import <stdio.h>
import <errno.h>
import <string.h>

FILE *f = fopen("nao_existe.txt", "r")
if f == NULL {
    printf("errno %d: %s\n", errno, strerror(errno))
}
```

```saida
errno 2: No such file or directory
```

O arquivo pelo `FILE *`. O `8.25` sai `8.2`: é o arredondamento do C (o
número exato fica no meio, e vale o par):

```ps
import <stdio.h>

FILE *f = fopen("notas.txt", "w")
fprintf(f, "%s=%.1f\n", "media", 8.25)
fclose(f)

char linha[80]
f = fopen("notas.txt", "r")
while (fgets(linha, sizeof(linha), f) != NULL) {
    printf("leu: %s", linha)
}
fclose(f)
remove("notas.txt")
```

```saida
leu: media=8.2
```

## 15.8. Callback, `atexit` e `exit`

Onde o C pede um ponteiro de função (`qsort`, `bsearch`, `atexit`), vai uma
funct da Jinga: ela vira um ponteiro de função de verdade pela libffi.

```ps
import <stdio.h>
import <stdlib.h>

int v[6] = {5, 3, 9, 1, 7, 2}

int funct compara(const void *a, const void *b) {
    return *(const int *) a - *(const int *) b
}

qsort(v, 6, sizeof(int), compara)
for each x in v {
    printf("%d ", x)
}
printf("\n")
```

```saida
1 2 3 5 7 9 
```

- A quantidade de parâmetros da funct é conferida contra o protótipo do
  callback antes de o C chamar (`qsort(): o argumento 4 é int (*)(const void
  *, const void *) no C, e um() recebe 1 argumento`).
- O erro dentro do callback não atravessa o C: as chamadas seguintes devolvem
  zero, e o erro sobe quando a função do C volta, com as duas linhas no
  traceback.
- `atexit(f)` registra uma funct que roda no fim do programa, com a VM viva,
  na ordem inversa do registro, também depois de um erro não tratado e no
  `sys.exit`. O `exit(n)` do C é o `sys.exit(n)`: os `finally` rodam, o
  `atexit` roda, e o programa sai com o código. O `quick_exit(n)` roda só o
  que foi registrado no `at_quick_exit`.

```ps
import <stdlib.h>

Null funct um() {
    post("um")
}

Null funct dois() {
    post("dois")
}

atexit(um)
atexit(dois)
post("fim do programa")
```

```saida
fim do programa
dois
um
```

## 15.9. O que derruba, de verdade

O ponteiro é de verdade: ponteiro errado, memória já liberada, divisão
inteira por zero no C derrubam o processo pelo sinal, como no C. Antes de
morrer, o motor escreve qual sinal foi, o endereço e a linha da Jinga, e
morre pelo mesmo sinal (o shell mostra o código: 139 no SIGSEGV). Não é
conferência: o ponteiro errado continua derrubando.

```ps
import <stdio.h>

int *p = NULL
printf("%d\n", *p)
```

```saida
```

```erro
Segmentation fault: memória inválida (endereço 0x0) na linha 4 de exemplo.pr
```

O tratador só é ligado na primeira vez que o programa usa o C: quem não usa
o C não paga nada.

## 15.10. O que fica de fora

Fica de fora, com erro claro e o motivo:

- `setjmp`/`longjmp`: pular por cima da VM corrompe a VM; a Jinga tem
  `try`/`catch`.
- O `<stdarg.h>` e as funções `v...` (`vprintf`...): o `va_list` só existe
  dentro de uma função variádica do C.
- O `<threads.h>` e o `<stdatomic.h>`: a VM roda numa thread só.
- O Anexo K (`printf_s`...): é opcional e não existe no Linux nem no macOS. O
  `gets` saiu do C11 (use `fgets`).
- O `<iso646.h>`: são outros nomes pros operadores; o `and`, o `or` e o `not`
  a Jinga já tem.
- O `true` e o `false` do `<stdbool.h>`: a Jinga usa `True` e `False`.
- O `<assert.h>`: o `assert` da Jinga faz esse papel.
- A gramática do C fora do que a biblioteca precisa: `for(;;)`, `switch`,
  `goto`, `#define`, `?:`, `do while`, o `enum` do C (a Jinga tem o dela), o
  ponteiro de função declarado (`int (*f)(int)`: a funct vai direto onde o C
  pede), o campo de bit em `struct`, e assembly.
